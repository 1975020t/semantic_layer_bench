## 7. 誤りパターンの分類

本実験（80回）の誤り11件を、生成SQL・応答文を読んで分類した。採点ロジックの誤判定はなかった（全件で生成SQLの意図と結果を確認済み）。

| パターン | 件数 | 該当 | 内容 |
|---|---|---|---|
| A. 曖昧語を独自に解釈 | 4 | q14 raw/comments、q16 raw/comments | 「安定した投手」を防御率で順位付け（用語集では WHIP）。「長打力」を長打率で測る（raw、打席の下限なし）、または ISO だが「打数1500以上」という独自の下限（comments） |
| B. DuckDB 方言の取り違え | 2 | q17 raw/comments | `(yearID / 10) * 10` で年代を作ろうとしたが、DuckDB の `/` は小数の割り算なので年がそのまま残り、5行ではなく50行になった（整数除算は `//`） |
| C. ウィンドウ関数の前に絞り込み | 2 | q19 comments/context | 2014年分を集計しておきながら、`LAG` と同じ SELECT の `WHERE` で2015年以降に絞ったため、2015年の前年比が NULL になった。raw は CTE を分けて正しく書けている |
| D. 列の意味の誤解 | 1 | q20 comments | Teams.G（そのチームの試合数）を両チーム分と解釈し、`SUM(G) / 2` で割って約2倍の値を出した |
| E. 定義外なのに回答（metrics） | 1 | q19 metrics | 前年比は表せないのに回答不能とせず、年別の本塁打数（2014〜2024年の11行）だけを返した |
| F. 定義外を正しく回答不能（metrics） | 1 | q16 metrics | 「ISO に当たる measure がなく、measure 同士の差も書けない」と回答不能を返した。正答率の上では不正解に数えている |

**偶然の正解**: q15「1990年代に最も成功した球団」で、raw と comments は「合計勝利数」で順位を付けたが、1990年代は最多勝利と最高勝率がともに ATL だったため、用語集の定義（勝率）と同じ答えになった。曖昧カテゴリの raw/comments の実力は、表の50%より低く見るべきである。

## 8. 考察

**1. 単純集計・派生指標・結合の罠は、このモデルではどの条件でも解けた（各12問すべて正解）。**
stint の合算、率を合計から再計算すること、teamID と franchID の違い（エンゼルスを `franchID = 'ANA'` で集計）は、テーブル名と列名しか渡さない raw でも正しく扱えた。応答文にも「移籍しているので stint を合算する」と書かれており、Lahman のような有名データではスキーマ知識がモデルの事前知識で補われている。社内データのように事前知識がないスキーマでは、この3カテゴリの差がもっと出ると考えられる。今回の結果からは「罠カテゴリでセマンティック情報が効く」とは言えない。

**2. 差がはっきり出たのは「曖昧な表現」で、効いたのは用語集だった。**
曖昧カテゴリは raw 50%、comments 50% に対して、用語集を渡した context は 100%、metrics は 75%（外れた1問は定義外の q16 で、回答不能を返した）。列の説明文（comments）だけでは「最強打者」「安定した投手」の業務上の定義は伝わらず、モデルはもっともらしい別の指標（防御率、長打率、勝利数）を選ぶ。業務用語の定義はカラムコメントではなく、用語集・指示として渡す必要がある。

**3. comments は raw より悪かった（75% 対 85%）。**
悪化した2問（q19 のウィンドウ、q20 の試合数の解釈）は、どちらも説明文の内容とは関係のない書き方の揺れである。q20 では「G: 試合数」という説明を読んで、かえって「両チーム分の試合数」と解釈を広げた可能性がある。20問・1回ずつの実験なので、1〜2問の差は誤差の範囲と見るのが妥当である（再現性確認でも raw は SQL が変わる）。

**4. 宣言的メトリクスは「定義内なら全問正解」だが、定義外の扱いが課題。**
metrics は定義内の18問をすべて正解した。DuckDB の割り算（B）、ウィンドウの書き方（C）、列の意味（D）といった SQL を書く条件で出た誤りは、構造上起こらない。率指標や join はコンパイラが定義どおりに作るため、モデルが選ぶのは measure・dimension・filter の名前だけになる。
一方で定義外の2問のうち、正しく回答不能を返したのは1問だけだった。q19 では「近い答え（年別の本塁打数）」を返しており、利用者からは誤りに気づきにくい。メトリクス定義を使う場合は、回答不能の判断を確実にする仕組み（定義外なら SQL を書く条件に回す、回答に「前年比は計算していない」と明示させる等）が要る。

**5. 再現性: temperature を指定できなくても、正誤は16組すべて一致した。**
Sonnet 5.5 は temperature を受け付けないため、拡張思考なし（between_tools）で実行した。2回の結果を比べると、正誤は 16/16、実行結果は 15/16 一致した。SQL の文字列が完全に一致したのは context と metrics では 8/8 だが、raw と comments では 3/8 にとどまった。結果が変わった1件（q14 raw）は、どちらも不正解のまま「規定投球回」の下限が 486 アウトから 300 アウトに変わったもので、曖昧な質問ほど出力が揺れる。用語集や例示を渡すと、答えだけでなく SQL の書き方まで安定する。

**6. トークン量。**
1回あたりの入力は raw 1,522 → comments 3,380 → context 6,037 トークンと増え、metrics は 4,518 だった。出力は逆に context（103）と metrics（125）が raw（171）・comments（174）より少ない。raw と comments では40件中14件が、「説明は書かない」という指示に反して前置きを書いた（解釈が分かれる質問で、自分の解釈を説明しようとする）。context は0件、metrics は2件（いずれも定義外の質問）だった。context は入力が raw の約4倍だが、正答率と出力の安定性は最も高かった。

## 9. Databricks への示唆

- **Metric Views** は粒度・率の再計算・join を定義側で保証できる。今回の metrics 条件で SQL 由来の誤りがなかったことに対応する。ただし前年比のようなウィンドウ計算は measure 定義の外になるため、Genie が SQL で補う構成か、YoY 用の measure・view を別に定義しておく必要がある。
- **Genie の Instructions** に用語集（「最強打者 = 規定打席以上で OPS 最高」など）を入れることが、曖昧な質問への対策として最も効いた。カラムコメントだけでは足りない。
- **Example SQL queries（trusted assets）** は、正答率への寄与を今回の実験だけでは用語集と切り分けられない。ただし SQL の書き方が安定した（再現性で SQL が 8/8 一致）。
- 「定義外のときに回答不能と言えるか」は 1/2 だった。本番では定義外の質問を検知してユーザーに伝える導線を用意したい。

## 10. 実験の限界

- 質問は20問、各条件1回（再現性確認は4問）。条件間の1〜2問の差に統計的な意味はない。
- Lahman はモデルが事前に知っている公開データで、選手IDや franchID まで知識で補える。事前知識のない社内スキーマでは結果が変わりうる。
- 質問文で出力列（選手ID・チームIDなど）を指定しているため、列の選び方による誤りは起きにくい設計になっている。
- metrics 条件にも用語集を渡している。context と metrics の差は「SQL を書くか、定義から選ぶか」の違いを見ている。
- 指定どおりの temperature=0 は、モデルの仕様上使えなかった（Kento さんの判断で Sonnet 5.5 を採用）。
